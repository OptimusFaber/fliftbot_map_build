# План единого пайплайна построения карты

Статус документа: черновик требований. Его можно редактировать перед реализацией.

## 1. Цель

Сделать один воспроизводимый пайплайн, который:

1. принимает сырые данные лидара, одометрии и опционально камеры;
2. приводит их к каноническому формату записи;
3. строит карту и траекторию Cartographer;
4. автоматически готовит изображения карты для web/navigation;
5. позволяет вручную скорректировать обрезку, ориентацию и начало координат;
6. переносит распознанные видеометки на карту;
7. может назначить выбранную метку началом локальной системы координат;
8. сохраняет все параметры и преобразования так, чтобы результат можно было
   повторить и без дополнительной ручной информации использовать в навигации.

## 2. Входные данные

Обязательные входы:

- `scan.*` — сырые данные лидара;
- один источник одометрии:
  - `*.log`; или
  - `*.csv`;
- `camera.config`;
- `lidar.config`;
- `liftbot.config`.

Опциональные входы для меток:

- видео;
- CSV с временными метками кадров;
- `labels2coords` и остальные данные декодера меток;
- идентификатор метки, которая должна стать точкой `(0, 0)`.

Для каждого поддерживаемого источника необходимо формально описать:

- единицы измерения;
- систему координат и направления осей;
- знак скорости;
- знак угла руления;
- timezone и смысл timestamp;
- формат `scan.*` и способ получения времени каждого скана/луча.

### 2.1. Зафиксированные примеры и форматы первой версии

Примеры находятся в `examples/`. Большие бинарные fixtures не требуется
копировать внутрь `map_build`, но тесты должны принимать путь к ним явно.

#### Move logger `*.log`

Пример:
`examples/fliftbot_move_logger_2026-10-07_10-10-04_Oct-07.log`.

Несмотря на расширение `.log`, это CSV с заголовком:

```text
t,x,y,dgr,nav_t,nav_x,nav_y,nav_dgr,enc_t,enc_v,enc_dgr,mode,plt,hw_err,sw_err,cmd_exec
```

Для canonical encoder разрешено читать только `enc_t`, `enc_v`, `enc_dgr`.
Поля `x/y/dgr` и `nav_x/nav_y/nav_dgr` не являются wheel encoder input и не
должны скрыто использоваться для построения карты. Timestamp
`1970_01_01_03_00_00_000` означает отсутствующие данные и отбрасывается.

`enc_t` имеет формат `%Y_%m_%d_%H_%M_%S_%f` без timezone suffix. Для этого
logger это локальное время `Europe/Moscow`; конвертер назначает timezone явно
и получает `enc_unix`. Наивный `datetime.timestamp()`, зависящий от timezone
машины запуска, запрещён.

После перевода `.log` в Unix time границы выбираются по фактической LiDAR-
записи. Берутся Unix timestamp первого и последнего сохранённых LiDAR-сканов;
для каждого из них в `.log` находится ближайший по абсолютной разнице
`enc_unix`. Все encoder-строки между двумя найденными индексами включительно
записываются в canonical. Произвольный временной запас по краям не добавляется.
В отчёте сохраняются LiDAR-границы, выбранные encoder-границы и обе ошибки
сопоставления в секундах. Если ближайшая граница дальше допустимого tolerance,
валидация должна выдать предупреждение или ошибку.

#### Wheel encoder `*.csv`

Пример: `examples/wheel_encoder_data.csv`.

```text
timestamp_sec,linear_velocity_m_per_s,wheel_angle_rad
```

- `timestamp_sec` — готовый Unix timestamp из `time.time()`;
- скорость задана в `m/s`;
- угол задан в радианах и при записи canonical переводится в градусы;
- весь CSV разрешено переносить в canonical;
- одинаковые timestamps дедуплицируются детерминированно, число удалённых
  дублей записывается в отчёт;
- пересечение с LiDAR всё равно валидируется.

#### Timestamps кадров `*.csv`

Пример: `examples/frame_timestamps.csv`.

```text
frame_index,time_take_img_sec
```

`frame_index` — индекс кадра видео, `time_take_img_sec` — Unix timestamp из
`time.time()`. Индексы проверяются на уникальность и допустимые пропуски.
При наличии `frame_index` кадры нельзя сопоставлять со строками только по их
порядку в файле.

#### Бинарный LiDAR-файл `scan.*`

Пример: `examples/scan.m360`. Расширение может отличаться, поэтому формат
определяется по содержимому. Данный пример имеет magic `M360RAW1`; далее идут
записи:

```text
float64 host_unix_time + 936 bytes raw DePHAN M360 UDP packet
```

`host_unix_time`, полученный при записи через `time.time()`, является общей
шкалой синхронизации с encoder и camera. Device timestamp пакета при
`time_sync=NONE` является uptime устройства и не используется как Unix time.
Один `horizon/*.npz` формируется на один полный оборот M360; времена лучей
берутся из host receive time соответствующих пакетов.

В первой версии это единственный обязательный бинарный LiDAR-формат. Другие
форматы пока не реализуются. Архитектура конвертеров при этом должна позволять
позднее добавить новый content-based decoder без изменения общего pipeline.

## 3. Структура каталогов

### 3.1. Самодостаточная директория инструментов `map_build`

Все используемые скрипты, конфигурации, схемы, шаблоны и локальные runtime-
зависимости должны находиться в одной директории `map_build/`. Пайплайн не
должен импортировать проектные Python-модули или запускать скрипты по путям за
пределами этой директории. Исключения допустимы только для системных
зависимостей: Python packages, ROS, Cartographer, OpenCV и других явно
перечисленных пакетов окружения.

Предлагаемая структура:

```text
map_build/
├── README.md
├── PIPELINE_TASKS.md
├── requirements.txt
├── build_from_raw.py
├── build_from_canonical.py
├── convert_recording.py
├── build_map.py
├── validate_recording.py
├── build_web_map.py
├── edit_web_map.py
├── process_markers.py
├── set_map_origin.py
├── validate_bundle.py
├── package_bundle.py
├── configs/
│   ├── current_version/
│   ├── schemas/
│   └── cartographer/
├── map_build_lib/
│   ├── converters/
│   ├── mapping/
│   ├── web_map/
│   ├── markers/
│   └── coordinates/
├── src/
│   ├── standalone_cartographer/
│   └── другие необходимые локальные компоненты
├── assets/
└── tests/
```

Верхнеуровневые скрипты должны быть тонкими CLI-обёртками. Общую логику
следует размещать в `map_build_lib/`, чтобы полный и поэтапный запуск не имели
двух расходящихся реализаций одного алгоритма.

Каждый CLI должен:

- поддерживать `--help`;
- возвращать ненулевой exit code при ошибке;
- печатать путь к созданному результату;
- сохранять фактические параметры запуска;
- не содержать абсолютных путей, зашитых под конкретный компьютер;
- корректно запускаться из любой текущей рабочей директории;
- иметь режим `--dry-run`, если команда создаёт много файлов или запускает
  Cartographer.

Предлагаемая структура одной обработанной записи:

```text
recordings/<recording_id>/

    │   ├── map.pgm
```

Разрешается хранить абсолютные пути и контрольные суммы в manifest, но
`canonical/` должен быть самодостаточным входом для построения карты.

## 4. Задачи реализации

### Задача 1. Инвентаризация и формальный контракт входов

- Описать варианты `scan.*`, `*.log` и `*.csv`.
- Зафиксировать обязательные поля и допустимые единицы.
- Запретить неявное угадывание timezone.
- Проверять монотонность timestamp, дубликаты, пропуски и нечисловые значения.
- Сохранять SHA-256 исходных файлов.

Результат: документированный контракт и валидатор входов.

### Задача 2. Конвертация `scan.*` в `horizon/*.npz`

- Реализовать адаптер для каждого формата `scan.*`.
- Для каждого NPZ сохранять минимум:
  - `xy` — точки в явно указанном frame;
  - `t` — timestamp каждого луча, если доступен;
  - `stamp` — timestamp скана;
  - `frame` — индекс кадра/скана.
- Не путать индекс `frame` с системой координат точек.
- Систему координат записывать в `lidar.config` через `points_frame`.
- Сохранять статистику количества кадров, точек, диапазона времени и
  отброшенных повреждённых записей.

Результат: `canonical/horizon/` и раздел `lidar_conversion` в
`conversion_report.json`.

### Задача 3. Конвертация одометрии в `encoder.jsonl`

- Поддержать `*.log` и `*.csv`.
- Нормализовать каждую запись к полям:

```json
{
  "enc_t": "исходное или читаемое время",
  "enc_unix": 1791383030.785,
  "enc_v": -0.278,
  "enc_dgr": 24.972,
  "enc_available": true
}
```

- Для `*.log`:
  - определить `[lidar_start_unix, lidar_end_unix]` из реально созданных NPZ;
  - найти в `.log` encoder sample с минимальным
    `abs(enc_unix - lidar_start_unix)`;
  - аналогично найти ближайший sample к `lidar_end_unix`;
  - взять диапазон между найденными строками включительно, без неявного
    временного padding;
  - сохранить ошибки выбора начала и конца в `conversion_report.json`;
  - не синхронизировать по строковому локальному времени;
  - записать исходный и выбранный диапазоны в отчёт.
- Для `*.csv`:
  - разрешить использовать весь файл;
  - всё равно проверить timestamp, порядок и пересечение с лидаром;
  - не обрезать автоматически, если это не включено отдельным параметром.
- Не изменять значения скорости и руления при конвертации. Знаки, scale,
  offset и wheelbase должны храниться как параметры модели, а не скрыто
  переписывать исходные данные.

Результат: `canonical/encoder.jsonl` и статистика синхронизации.

### Задача 4. Проверка синхронизации

- Вывести начало/конец лидара и энкодера в Unix seconds и ISO 8601 UTC.
- Проверить наличие encoder samples на всём интервале лидара.
- Посчитать частоту данных, максимальный gap, число дублей и долю движения.
- Предупреждать, если во время работы лидара скорость всегда равна нулю.
- Опционально оценивать постоянный временной offset по согласованию угловой
  скорости LiDAR-траектории и энкодера, но никогда не применять найденный
  offset молча.

Результат: явный статус `accepted`, `accepted_with_warnings` или `rejected`.

### Задача 5. Построение карты

- Использовать канонические `horizon/` и `encoder.jsonl`.
- Поддержать режимы:
  - `lidar_only`;
  - `lidar_plus_odometry`.
- Все параметры одометрии сохранять в `run_parameters.json`:
  - `wheelbase_m`;
  - `encoder_speed_sign`;
  - `steering_sign`;
  - `steering_offset_deg`;
  - `odometry_time_offset_s`;
  - применённые фильтры.
- Сохранять точную копию использованного Lua-конфига или его SHA-256.
- Сохранять:
  - `map.pbstream`;
  - `map.pgm`;
  - `map.png`;
  - `map.yaml`;
  - `trajectory.json`;
  - `track.png` — карта с траекторией робота;
  - статистику Cartographer и число constraints.
- Явно указывать, относится `trajectory.json` к лидару или к оси погрузчика.
  При необходимости сохранять обе траектории разными файлами.

### Задача 6. Автоматическая подготовка `web_map`

Автоматический алгоритм должен:

1. загрузить occupancy map и её метрические параметры из `map.yaml`;
2. удалить далёкие одиночные лучи и небольшие несвязные компоненты;
3. найти полезную область карты и обрезать фон с настраиваемым margin;
4. определить основные направления стен;
5. выбрать угол, при котором максимум длинных стен параллелен `Ox/Oy`;
6. повернуть изображение без потери полезной области;
7. повторно обрезать пустые края;
8. привести изображение к целевому разрешению, например `0.01 м/px`;
9. сформировать тёмную и светлую версии;
10. сохранить все преобразования и параметры.

Для ориентации стен предусмотреть устойчивый метод:

- бинаризация занятых ячеек;
- Hough/LSD для длинных линий;
- кластеризация углов по модулю `90°`;
- взвешивание по длине линии;
- отказ от автоматического выравнивания при низкой уверенности.

При нескольких помещениях стены не обязаны образовывать одну связную
компоненту. Угол определяется по всем достаточно длинным стенам-кандидатам.
Выбирается ортогональное семейство направлений с наибольшей суммарной
поддержкой по длине и числу линий. Несоединённые параллельные стены должны
учитываться совместно; небольшое локальное помещение не должно перевешивать
основное направление большинства стен.

Удаление далёких лучей не должно стирать настоящие стены. Поэтому нужны:

- минимальная площадь/длина компоненты;
- максимальная дистанция от основной связной области;
- сохранение исходной карты;
- изображение-превью с отмеченными удаляемыми пикселями;
- численный confidence и возможность отключить фильтрацию.

Результат:

- `web_map/map_dark.jpg`;
- `web_map/map_light.jpg`;
- матрицы преобразований;
- `web_map/map_metadata.json`;
- `web_map/edit_recipe.json` с crop, rotation, scale и выбранным origin.

Стандартное разрешение web-карты — `0.01 м/px` (`1 см/px`). Оно применяется
по умолчанию, но переопределяется аргументом
`--web-resolution-m-per-px`; фактическое значение всегда записывается в
metadata и матрицы.

После автоматического выравнивания и crop начало локальной системы координат
по умолчанию находится в центре нижнего левого пикселя полезного изображения:
`+X` направлена вправо, `+Y` вверх. Для стандартной автоматически созданной
карты видимые локальные координаты поэтому неотрицательны.

### Задача 7. Контракт координат и матриц

Нельзя использовать одно неоднозначное слово «homography» для разных систем.
Нужно хранить три явных преобразования в homogeneous coordinates:

1. `pbstream_to_local_matrix.npy`:
   `Cartographer map XY [m] -> local navigation XY [m]`;
2. `map_transform_matrix.npy`:
   `local navigation XY [m] -> image UV [px]`;
3. `pbstream_to_raster_matrix.npy`:
   `Cartographer map XY [m] -> image UV [px]`.

Должно выполняться:

```text
pbstream_to_raster = map_transform_matrix @ pbstream_to_local
```

Для изображения используется:

```text
U направлена вправо
V направлена вниз
```

Для навигации:

```text
X направлена вправо/вперёд согласно выбранному контракту
Y направлена вверх/влево согласно выбранному контракту
единицы — метры
```

Точное направление локальных осей и положение `(0, 0)` обязательно записать
в `map_metadata.json`. В отличие от текущего примера
`calculate_homography_matrix.py`, scale должен входить в матрицу явно:
для `0.01 м/px` коэффициент равен `100 px/m`.

JSON должен дублировать матрицы в читаемом виде, чтобы результат можно было
проверить без загрузки NumPy-файла.

### Задача 8. GUI ручной коррекции карты

Сделать отдельный инструмент, который открывает исходную карту и позволяет:

- задать прямоугольник или полигон обрезки;
- изменить угол поворота;
- выбрать точку `(0, 0)` кликом;
- выбрать направление положительной оси `X` вторым кликом или числом;
- включить/выключить найденные автоматически выбросы;
- увидеть координаты курсора одновременно в px, local metres и PBStream XY;
- просмотреть `dark/light` до сохранения;
- отменять действия и возвращаться к автоматическому варианту.

GUI не должен редактировать исходные файлы. Он сохраняет `edit_recipe.json`,
после чего обычный headless-скрипт воспроизводит итоговые изображения и
матрицы. Это позволит повторить ручную правку на другой машине.

### Задача 9. Извлечение и перенос видеометок

Если переданы видео и CSV времён кадров:

- проверить, что timestamps камеры находятся в том же Unix-domain;
- получить/загрузить detections и `observations.json`;
- интерполировать позу робота/лидара на timestamp кадра;
- перенести луч камеры в систему Cartographer;
- определить координаты метки;
- объединить повторные наблюдения одной физической метки;
- сохранить число наблюдений, разброс и confidence;
- сохранить координаты одновременно в:
  - `pbstream_map_xy_m`;
  - `local_navigation_xy_m`;
  - `raster_uv_px`.

Результат: `markers/markers_map.json` и изображение карты с метками.

Идентичность физической метки определяется прежде всего устойчивым track, а
не результатом декодера. Каждому найденному физическому track присваивается
собственный стабильный `marker_id`/`track_id`. Для него дополнительно
сохраняются результаты `labels2coords`:

- `decoded_label` — наиболее частая валидная метка среди наблюдений track;
- `decoded_label_votes` — histogram всех полученных значений;
- `decoded_label_confidence` — доля победившего значения;
- количество undecoded/invalid наблюдений;
- признак конфликта, если два близких по частоте label претендуют на track.

Два разных физических track нельзя автоматически сливать только потому, что
декодер выдал им одинаковый label. На первом этапе итоговым label считается
мода, то есть самое частое значение. При равенстве или почти равном количестве
голосов, а также при недостаточной уверенности, `decoded_label` записывается
строкой `"?"`. Пайплайн не останавливается и не требует немедленного ручного
выбора: собственный `marker_id`, histogram голосов и все наблюдения track
сохраняются, чтобы label можно было исправить позднее.

### Задача 10. Перенос начала координат на выбранную метку

Сделать отдельную команду, например:

```bash
python3 set_map_origin.py \
  --web-map results/<run_id>/web_map \
  --markers results/<run_id>/markers/markers_map.json \
  --origin-marker 42
```

Команда должна:

- найти устойчивую оценку координат выбранной метки;
- создать новое `pbstream_to_local_matrix.npy`, в котором эта метка имеет
  координаты `(0, 0)`;
- пересчитать зависимые матрицы и координаты всех меток;
- не менять пиксели карты без необходимости;
- сохранить идентификатор метки, старую и новую матрицы;
- поддержать дополнительный выбор направления `+X`:
  - оставить направление автоматического выравнивания стен;
  - задать угол вручную;
  - направить `+X` от origin-marker к другой метке.

Важно: смена origin — это композиция матриц, а не ручное изменение координат
каждого объекта.

Поведение изображения и origin:

- автоматический web-map по умолчанию имеет `(0,0)` в левом нижнем углу;
- если пользователь назначает метку началом координат, меняется логическая
  локальная система и матрицы, но пиксели/crop изображения не перемещаются;
- выбранная origin-метка после этого может находиться в любой точке картинки;
- повторная компоновка изображения вокруг нового origin допускается только
  отдельной явной опцией, а не как побочный эффект `set_map_origin.py`.

### Задача 11. Навигационный manifest

Создать единый `web_map/map_metadata.json`, содержащий минимум:

```json
{
  "schema": "fliftbot.web_map.v1",
  "images": {
    "dark": "map_dark.jpg",
    "light": "map_light.jpg"
  },
  "resolution_m_per_px": 0.01,
  "image_size_px": [0, 0],
  "origin": {
    "type": "automatic|manual|marker",
    "marker_id": null
  },
  "coordinate_frames": {},
  "matrices": {},
  "source_map": {},
  "automatic_alignment": {},
  "manual_edit": null
}
```

В JSON также сохранить версии скриптов, параметры запуска, SHA-256 исходной
карты и список созданных файлов.

### Задача 11.1. Runtime-контракт с `realtime_mapping`

Существующая live-локализация использует следующий комплект:

- `map.pbstream` — обязательное сериализованное состояние Cartographer для
  continuous pure localization;
- `origin_reference.json` или совместимый `marker_reference` — обязательная
  привязка `cartographer_map` к локальным координатам навигации;
- согласованный профиль лидара и одометрии: mount, sensor yaw, speed sign,
  steering zero, wheelbase и модель `sin/tan`.

`map.pgm + map.yaml` нужны для occupancy-визуализации, RViz и одноразовой
глобальной локализации, но не заменяют PBStream в continuous Cartographer
localization. `web_map/*.jpg` предназначены для web/UI и также не заменяют
PBStream.

`package_bundle.py` должен только создавать deploy-поднабор, который при
желании можно вручную передать в `realtime_mapping` или положить в
`realtime_mapping/maps/<map_name>/`:

```text
map.pbstream
origin_reference.json
map.pgm
map.yaml
map.png
map_metadata.json
```

`origin_reference.json` должен быть совместим с текущим
`live_marker98_pose.py`:

```json
{
  "schema": "fliftbot.map_origin_reference.v1",
  "frame": "cartographer_map",
  "origin_name": "web_map_lower_left|marker_<id>",
  "origin_map_xy_m": [0.0, 0.0],
  "origin_map_yaw_rad": 0.0,
  "origin_map_yaw_deg": 0.0,
  "axis_contract": "+X ..., +Y ...",
  "source": "map.pbstream"
}
```

`realtime_mapping` загружает `map.pbstream`, публикует локализованную позу в
Cartographer frame `map`, затем `live_marker98_pose.py` преобразует её через
reference. Выход для ContinuousNav остаётся `[x_m, y_m, yaw_rad]` в выбранной
локальной системе. Web-матрицы являются дополнительными артефактами и не
должны менять этот runtime-контракт.

Упаковщик не копирует файлы в `realtime_mapping`, не меняет
`config/lidar_profiles.json` и не переключает активную карту. Подключение
новой карты выполняется пользователем отдельно после проверки результата.

### Задача 12. Набор CLI-скриптов

Пайплайн должен состоять из нескольких независимых скриптов. Каждый этап
можно запускать отдельно, а полный скрипт вызывает те же самые функции по
очереди.

#### 12.1. `build_from_raw.py` — полный цикл из сырых данных

Главная команда для обычного использования. Она выполняет:

```text
raw validation
  -> conversion to canonical
  -> canonical validation
  -> Cartographer mapping
  -> trajectory rendering
  -> web-map generation
  -> marker processing, если заданы входы камеры
  -> origin relocation, если задана origin-marker
  -> final validation
  -> packaging/manifest
```

Предлагаемый верхнеуровневый интерфейс:

```bash
python3 map_build/build_from_raw.py \
  --scan /path/to/scan.m360 \
  --odometry /path/to/data.log \
  --camera-config /path/to/camera.config \
  --lidar-config /path/to/lidar.config \
  --robot-config /path/to/liftbot.config \
  --recordings-root /path/to/recordings \
  --results-root /path/to/results \
  --name warehouse_a
```

#### 12.2. `convert_recording.py` — только создание canonical recording

Принимает `scan.* + log/csv`, выполняет синхронизацию и создаёт:

```text
canonical/horizon/*.npz
canonical/encoder.jsonl
canonical/*.config
canonical/conversion_report.json
```

Cartographer этим скриптом не запускается. Команда нужна для проверки
конвертации и повторного использования одной записи в нескольких mapping-
экспериментах.

#### 12.3. `build_from_canonical.py` — полный цикл из обработанных данных

Принимает готовую canonical-директорию с `horizon/`, `encoder.jsonl` и
конфигами. Пропускает raw-конвертацию, но выполняет весь последующий pipeline:

```text
canonical validation
  -> mapping
  -> trajectory rendering
  -> web-map generation
  -> marker processing, если переданы video-входы
  -> origin relocation, если задана origin-marker
  -> final validation
  -> packaging/manifest
```

Не читает исходные `scan.*`, `log` или `csv` и не изменяет canonical-файлы.

Пример:

```bash
python3 map_build/build_from_canonical.py \
  --recording recordings/<recording_id>/canonical \
  --output results \
  --name warehouse_a_odom
```

#### 12.4. `build_map.py` — только Cartographer и траектория

Принимает canonical recording и создаёт только mapping-артефакты:

```text
map.pbstream
map.pgm
map.png
map.yaml
trajectory.json
track.png
run_parameters.json
```

Этот скрипт нужен для экспериментов с параметрами Cartographer и одометрии,
когда конвертация, web-map и распознавание меток не должны запускаться заново.

#### 12.5. `build_web_map.py` — генерация web/navigation-карты

Принимает результат mapping с `map.pgm`, `map.yaml`, `map.pbstream` и
`trajectory.json`. Выполняет автоматическую очистку, выравнивание, crop,
масштабирование, создание `dark/light` и всех координатных матриц.

Скрипт должен уметь работать в двух режимах:

- полностью автоматически;
- по готовому `edit_recipe.json`, сохранённому GUI.

Он не должен повторно запускать Cartographer.

#### 12.6. `edit_web_map.py` — интерактивное редактирование

Запускает GUI для ручной корректировки:

- удаляемой области;
- crop;
- угла;
- масштаба, если это разрешено контрактом;
- начала координат;
- направления `+X`.

GUI сохраняет только `edit_recipe.json` и preview. Итоговые файлы создаются
через ту же библиотечную функцию, что использует `build_web_map.py`.

#### 12.7. `process_markers.py` — поиск и перенос меток

Принимает видео, timestamps кадров, параметры камеры, данные декодирования и
готовую траекторию. Выполняет:

```text
video detections
  -> observations
  -> temporal pose interpolation
  -> marker projection
  -> robust aggregation
  -> conversion to local/raster coordinates
```

Должен поддерживать два режима:

- полный поиск меток непосредственно из видео;
- перенос уже готового `observations.json` без повторной обработки видео.

Не должен перестраивать карту или изменять исходную траекторию.

#### 12.8. `set_map_origin.py` — перенос системы координат

Принимает готовый `web_map`, координаты меток или точку, выбранную вручную.
Меняет origin и при необходимости ориентацию локальных осей через композицию
матриц. Не запускает Cartographer и не обрабатывает видео повторно.

#### 12.9. `validate_recording.py` — диагностика входных данных

Проверяет raw или canonical recording отдельно от тяжёлого pipeline:

- временные диапазоны;
- timestamps и gaps;
- поля NPZ/JSONL;
- единицы и конфигурации;
- пересечение LiDAR/encoder/camera;
- подозрительно нулевую одометрию.

Поддерживает человекочитаемый вывод и машинный JSON-report.

#### 12.10. `validate_bundle.py` — проверка готового результата

Проверяет наличие артефактов, матрицы, round-trip координат, попадание
траектории/меток в изображение и соответствие manifest фактическим файлам.
Этот скрипт должен запускаться в конце полного pipeline и отдельно перед
передачей карты в навигацию.

#### 12.11. `package_bundle.py` — упаковка для переноса

Создаёт самодостаточный архив или директорию результата для навигационного
компьютера. Включает только необходимые runtime-файлы и manifest с SHA-256.
Исходные видео, raw scan и временные файлы не включаются, если это явно не
запрошено.

### Общие опции полного запуска

Опциональные аргументы `build_from_raw.py`:

```text
--video
--frame-timestamps
--labels2coords
--origin-marker
--lidar-only
--manual-web-map
--web-resolution-m-per-px 0.01
--odometry-time-offset
```

Пайплайн должен поддерживать повторный запуск с этапа:

```text
convert -> validate -> map -> web-map -> markers -> set-origin -> package
```

Это позволит не перестраивать Cartographer после изменения только crop или
начала координат.

Можно дополнительно предоставить `map_build.py` как диспетчер подкоманд:

```bash
python3 map_build/map_build.py convert ...
python3 map_build/map_build.py map ...
python3 map_build/map_build.py from-canonical ...
python3 map_build/map_build.py web-map ...
python3 map_build/map_build.py markers ...
python3 map_build/map_build.py edit ...
python3 map_build/map_build.py validate ...
python3 map_build/map_build.py all ...
```

Это только единая точка входа. Самостоятельные скрипты из разделов выше всё
равно должны оставаться доступными.

## 5. Проверки качества

Перед выдачей результата автоматически проверять:

- временное пересечение LiDAR/encoder/camera;
- число и частоту сканов;
- наличие движения в encoder;
- конечное число Cartographer constraints;
- существование и читаемость всех обязательных артефактов;
- обратимость матриц;
- равенство композиции матриц с заданной погрешностью;
- round-trip `map XY -> pixel -> map XY`;
- попадание траектории и меток в границы web-карты;
- отсутствие изменения результата при повторном запуске с тем же recipe;
- отсутствие использования GT/navigation-файлов при построении карты.

Для A/B-проверок сохранять минимум:

- карту только по лидару;
- карту с одометрией;
- наложение двух траекторий;
- численные метрики расхождения.

## 6. Критерии готовности

Пайплайн считается готовым, когда:

1. `build_from_raw.py` создаёт полный результат из `scan.* + log/csv`;
2. `build_from_canonical.py` создаёт тот же downstream-результат без повторной
   raw-конвертации;
3. каждый крупный этап можно вызвать отдельным CLI;
4. все проектные скрипты и необходимые локальные файлы находятся внутри
   `map_build/`;
5. `web_map` создаётся автоматически и воспроизводимо;
6. GUI сохраняет recipe, который можно повторить без GUI;
7. метки получают координаты во всех трёх системах;
8. origin можно перенести на выбранную метку без перестроения карты;
9. `realtime_mapping` получает согласованные `map.pbstream` и
   `origin_reference.json`, а остальные потребители находят occupancy/web
   артефакты через `map_metadata.json`, без скрытых констант;
10. каждый результат содержит параметры, версии и контрольные суммы.

## 7. Предлагаемый порядок реализации

1. Создать каркас самодостаточной директории `map_build/` и перенести туда
   используемые скрипты, конфиги и локальные зависимости.
2. Контракты форматов и конвертеры `scan/log/csv`.
3. Синхронизация и `conversion_report.json`.
4. Стабильный headless mapping и полный manifest запуска.
5. Контракт координат и три матрицы преобразования.
6. Автоматический `web_map`.
7. GUI для crop/rotation/origin и воспроизводимый recipe.
8. Перенос меток.
9. Перенос origin на метку.
10. Интеграционные тесты и упаковка результата для навигации.
