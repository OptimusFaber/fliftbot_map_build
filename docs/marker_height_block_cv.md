# Высота меток по независимым участкам трека

## Текущее решение

`ceiling_marker_localization_stored_ray_corrected.py` строит карту по сохранённым
лучам `observations.json`. Для режима независимых высот используется
`--per-track-height`. Экспериментальный, проверенный на двух записях режим
`--height-quality-method block_cv` делит каждый трек на участки после каждых
0,20 м перемещения камеры. Затем четыре раза повторяет подгонку высоты,
исключая очередную четверть участков. Высота считается самостоятельной, если
изменение относительно полного трека не превосходит 0,30 м и прежняя оценка
неопределённости не превосходит 0,25 м. Пороги задаются через CLI.

Слабый трек сохраняется. Если его лучи однозначно указывают на соседнюю метку
с надёжной высотой, он присоединяется к ней без участия в расчёте высоты.
Иначе остаётся отдельным кандидатом с `ceiling_z_m: null`. Все исходные
кандидатные треки перечислены в `track_height_quality` итогового JSON; там же
есть число пространственных участков и четыре повторные оценки высоты.
`marker_id` зависит от сортировки точек и не служит постоянным идентификатором.
В сохранённых результатах все 893 и 947 принятых треков соответственно
встречаются в итоговых точках ровно по одному разу.

## Повторный расчёт карты

При наличии готовых observations запускать из корня репозитория:

```bash
python src/map_build/process_markers.py \
  --run-dir "$RUN" \
  --observations "$OBS" \
  --camera-position "$CAMERA_POSITION" \
  --camera-json "$CAMERA_JSON" \
  --lidar-config "$LIDAR_CONFIG" \
  --out-dir "$OUT" \
  --per-track-height --stationary-height-filter \
  --min-camera-baseline-m 0.75 --merge-radius-m 0.6 \
  --height-quality-method block_cv \
  --block-distance-m 0.20 --max-block-height-instability-m 0.30
```

Для записи `20261029_124432_nav_video` дополнительно использовался
`--max-marker-height-m 14.5`; для `20261029_004258_nav_video` ограничение
высоты не применялось. `RUN/map/trajectory.json` и `RUN/map` берутся по
`--run-dir`. Если входы лежат в другом месте, указывайте их явно, как в
команде выше. Результат содержит `marker_points_stored_ray_corrected.json`,
`stored_ray_corrected_map.png` и крупный план.

`--height-quality-method legacy` воспроизводит прежнюю проверку без проверки
по участкам пути. По умолчанию оставлен `legacy`: включать новый режим явно,
пока не решено объединение двух слабых треков одной метки.

## Оценка на складе

GT используется только отдельным оценочным скриптом после построения карты.
Его преобразование в систему карты зафиксировано в
`evaluate_transferred_markers.py` для склада Нижбел и не подбирается по
новому результату:

```bash
python src/fliftbot_mapping/evaluation/evaluate_transferred_markers.py \
  --marker-dir "$OUT" --map-dir "$RUN/map" \
  --gt /path/to/labels2coords.json
```

| Запись | Метод | GT совпадений | Известна высота | Медиана высоты | P95 высоты | Медиана XY | Медиана соседей |
|---|---|---:|---:|---:|---:|---:|---:|
| 00:42 | legacy | 396 | 396 | 4,92 см | 19,19 см | 16,76 см | 3,84 см |
| 00:42 | block_cv | 396 | 386 | 4,73 см | 15,92 см | 16,76 см | 3,78 см |
| 12:44 | legacy | 402 | 401 | 4,23 см | 20,13 см | 17,90 см | 4,18 см |
| 12:44 | block_cv | 402 | 389 | 4,01 см | 16,47 см | 17,84 см | 4,07 см |

Ошибка высоты уменьшилась среди точек, для которых высота выдана. Покрытие
снизилось: число верных высот с ошибкой до 20 см изменилось с 380 до 376 и с
380 до 378 соответственно. Трек 398 старой записи больше не выдаёт
ошибочную высоту, но пара слабых треков 397/398 пока остаётся двумя
кандидатами. Поэтому `block_cv` ещё не считается окончательной картой меток.

Проверялся также `--cross-pass-height-consensus-m 0.30`. Он не улучшил
покрытие или ошибки на этих двух записях; оставлен только как исследовательский
параметр и не включён в команду выше.
